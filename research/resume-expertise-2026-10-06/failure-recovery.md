# 异常场景与恢复要求

2026-10-06 只读审计与设计草案。检查了关键代码和相关测试文件，未运行测试、未访问生产数据、未修改业务代码。以下“已有保护”指实现或测试用例存在，不代表本轮实测通过；“明确缺口”指静态代码可定位的问题；“未验证”需要专项复现。

目标：失败时让用户知道哪里出了问题、哪些内容仍在、当前稿是否变化，以及怎样继续。无法预先枚举所有错误，因此每一步都需要统一的恢复约定和后续故障注入验证。

## 共同恢复约定

1. **准确报告完成阶段。** 上传接收、文本提取、经历识别、模型分析、建议核验、写入、导出分别记录。收到 HTTP 200 或对话正常结束，不自动等于业务成功。
2. **保留可恢复的工作。** 本页输入、附件和候选改写应能重试；跨刷新恢复若要新增持久存储，沿现有受限、加密和过期机制设计，不把明文简历写进长期浏览器缓存。没有持久恢复能力时明确说明范围。
3. **区分未写入、已写入、结果待确认。** 网络中断不能一律显示“没有保存”；未知结果先查询当前版本和建议状态，不盲目重新提交。
4. **按操作决定重试。** 只读读取可有次数和超时限制；写入依靠建议或操作标识、版本检查来防重；鉴权失效先恢复身份，不循环请求。外部调用是否实际停止或计费不能由客户端取消推断。
5. **允许继续完成任务。** 按原因提供重试、粘贴文字、上传可读文件、手动修改、保留原稿等路径；系统解析或匹配问题不能伪装成用户缺事实。
6. **留下可诊断记录。** 记录阶段、错误类别、请求标识和稿件版本，避免记录完整私人简历、验证码或密钥。对用户显示行动说明，不暴露内部堆栈。

这些要求参考 [Google PAIR 的错误与恢复指南](https://pair.withgoogle.com/guidebook-v2/chapter/errors-failing/) 和 [Microsoft Human-AI Interaction 指南](https://www.microsoft.com/en-us/research/project/guidelines-for-human-ai-interaction/)，落实到本项目的恢复动作和优先级是我们的设计。资料支持让用户能理解、纠正和继续任务，不能替代以下代码验收。

## 材料与工具

| ID | 场景与当前观察 | 拟议处理与验收 |
|---|---|---|
| E01 | 扫描或空文本 PDF：明确缺口。提取为空仍返回成功，显示 0 字且可发送；无扫描 PDF OCR 回退 | 标为未读出而非已导入，给可读文件、文字或可支持图片路径；没有已配置 OCR 就不宣称能自动识别。空文件不得悄悄成为成功材料 |
| E02 | 加密、损坏、超页数、超大小文件：局部覆盖。有大小、页数、解压和超时限制；部分失败统一提示格式错误 | 区分需解锁、损坏、不支持、超限；成功附件继续保留。限额在上传前说明，处理失败不让用户重传全部文件 |
| E03 | 多附件合并超限：明确缺口。单文件可提取 6000 字，发送单消息上限 10000 字；各自上传成功仍可能合并后 413。失败恢复文字，不恢复附件列表 | 上传与发送使用一致总量预算；超限时预告并允许分批。发送失败后附件 chips 和顺序可恢复，不重复导入已成功部分 |
| E04 | 部分附件未识别：局部覆盖。识别成功的材料可合并，但被过滤附件没有逐文件失败清单 | 每份显示已识别、部分识别、未识别及原因；让用户区分“已收集但没选入”和“根本未读到” |
| E05 | 重复经历、角色/时间冲突：局部覆盖。同名合并、精确文本去重及部分字段冲突有测试；自由文本中的不同指标未通用协调 | 保留来源和时间，明确更正与未知冲突分开处理；更名或同名不同项目不误合并；只问影响当前稿的冲突 |

| E07 | 多链接、私网和重定向：安全检查已有；多链接不自动触发读取，但缺专门选择入口 | 多个公开链接让用户选择当前要读的一个；被拒地址不重试绕过。保持已验证的私网、端口、凭证和重定向限制 |
| E08 | 网页超时、403、动态登录页：已有失败回退；自然语言读取公开链接的专用重试入口未完整覆盖 | 保留链接和草稿，按读取方式统一重试或贴正文/截图；不因读取失败清空现有 JD 或当前简历 |
| E09 | 搜索空结果、旧结果、分析失败：后端有说明；外围工具状态可能仍写分析已完成，该 UI 风险未实测 | 来源获取、有效性和分析状态分开；无结果不等于不存在，获取日期不等于发布日期。找旧岗位须明确未核实开放状态 |
| E10 | 搜索未配置或运行中失效：已有不可用入口和失败提示 | 配置存在只代表可以尝试；服务实际失败时提示替代路径，保留输入，不显示已核实或回显敏感服务响应 |

## 提示文案应该说清什么

以下是目标文案，只有状态查询已确认后才能按对应状态展示：

- 已确认无写入：“这次建议没有生成成功，当前简历未改动。你的改写要求还在，可以重试或继续手动编辑。”
- 写入结果未知：“连接中断，正在核对这次修改是否已保存。先保留当前内容，确认后再重试。”
- 部分材料成功：“两份资料中一份已识别；另一份没有读出文字。你可以先用已识别内容继续，或补充那份资料。”
- 保存失败：“最新修改尚未保存。先重试保存；也可以明确选择导出最近一次已保存的版本。”

提示必须与实际按钮和能力相符；若未实现自动核对，不能显示“正在核对”。避免长错误堆栈、只说请稍后再试，或系统问题一律要求用户补事实。

## 下一轮优先级与验证

首批优先消除静默遗漏和不确定写入：E01/E03/E04 的导入回执及重试、建议对象绑定与原文依据误报、E13 的结果核对、E15/E16 的保存导出和身份恢复。其次统一截断、无结果、迟到响应和各入口状态；其他场景按影响程度补齐。

不需要无差别重跑整个系统。针对每项修改，用故障注入验证失败前后稿件版本、输入和附件状态、重复请求结果、恢复后的导出内容。候选首批用例：

- 空文本 PDF；两份长文件分别成功但合计超限；其中一份解析失败；不完整附件仍被明确标出。
- 同一建议连点；服务端提交成功后丢弃响应；版本冲突；恢复后还能撤销。
- 生成中断、保存永不返回、401、会话切换后迟到响应；均不串稿、不误报成功。
- 搜索无来源或模型分析失败；工具状态和对话文案一致。
- 长简历渲染越界；优先信息不被截掉，PDF/Word 与已采用版本一致。

测试材料存在漂移：`tests/resume_persistence.browser.js:104` 仍期待 sessionStorage 跨刷新恢复，而 `web/resume-editor.js:99` 使用 memory-only。旧测试报告不能证明当前刷新恢复；应先对齐预期，再记录本轮新结果。已有用例存在与当前通过应分别报告。

最终交付按“正常完成、部分完成、失败可恢复、结果待确认”分别验收。专业建议本身好不好，与异常时能不能继续，是两条都必须通过的产品质量线。
