## 二、用户实测反馈：对话流程跑不通（第十四批要解决）

真实对话：用户从零开始聊，方向是 AI 产品，素材是一个个人开发并已上线的 AI 简历项目。成稿只有一个项目栏目，标题是 `[待补]`，要点是用户原话照搬。

| 现象 | 根因（代码位置） |
|---|---|
| 每轮下方都挂一张「接着当前问题」卡片，与正文重复 | `backend/app/services/resume_workspace.py` 约 365–386 行：`_reply_question()` 用正则从模型回复中**抠出问题句**做卡片；没有选项时只剩「在下方直接回答」 |
| 方案卡「写法：问题-决策-结果」点了就直接发送，而且没生效 | `web/resume-workspace.js` 约 482–486 行：写法按钮直接调用 `answer('写法：…')` 发消息；后端不认这条消息，又弹出同一张方案卡；只有「按推荐写」有效 |
| 回答「不知道」后，同一个问题（多少人在用）再问一遍 | 缺失项按字段计算；「不知道 / 跳过」没有把该项标记为已回答、关闭 |
| 简历要点是用户原句，标题 `[待补]`，只有一个栏目 | 抽取把用户句子原样存成事实，写作阶段没有改写（或改写被事实校验拦下后退回原句，**需回放确认**）；从未收集项目名称、时间和基本信息 |
| 追问方向不对 | 按「缺字段 / 要量化」套模板；个人开发的 AI 产品项目被追问用户数。AI 产品岗看重的是问题定义、关键产品决策、迭代与 badcase、技术栈、上线现状 |

质量标杆：用户提供的参考简历 用户本机的参考简历 PDF（含个人联系方式，**不入库、不外传**）。其中「胡话简历」一段的写法是：项目名 + 一句定位，下面「问题 / 决策 / 迭代」三行，每行写具体的决策或事件。

## 三、第十四批规格：分阶段对话 + 结构化问题卡（GenUI）

### 1. 问题卡由模型通过工具调用直接生成（核心改动）
- 新增工具 `ask_user`，由模型决定何时调用，**不再从文本中抠问题**。参数示意：
  ```json
  {"questions": [
    {"id": "problem", "prompt": "解决谁的什么问题？", "kind": "text", "placeholder": "一句话"},
    {"id": "my_work", "prompt": "你本人做了哪些？", "kind": "multi",
     "options": ["想需求", "写提示词", "做原型", "技术开发", "找用户试用"], "allow_other": true},
    {"id": "status", "prompt": "现在什么状态？", "kind": "single",
     "options": ["只有想法", "原型能跑", "有人在用", "已上线"], "allow_other": true}
  ]}
  ```
- 前端：在输入框上方显示翻页卡片（1 of N）。单选点击即选中，多选可勾多个，统一用「提交」发送；每题都可「跳过」，都有「其他」自填。提交后拼成一句可读的话作为用户消息发出，同时附带结构化答案。
- 规则：调用了 `ask_user` 的那一轮，正文只写过渡语，不写问题；纯开放问题不出卡片。
- 删除 `_reply_question` 生成卡片的路径；方案卡的「写法」改成切换选中态，随「按推荐写」一起提交。

### 2. 分阶段流程
1. **基本信息**（首次使用）：一张表单，含姓名、学校 / 专业 / 学历、毕业时间、城市、可实习时间，可以跳过；已登录用户从档案预填，只需确认。
2. **目标岗位**：贴 JD 或链接，或者只给一个方向（只给方向时，第十五批接入「岗位画像」）。
3. **经历清单**：快速添加小框，每段填名称、起止时间、角色、一句话简介，从源头消除 `[待补]`。
4. **逐段深挖**：每段按 `role-playbooks/<岗位>.md` 问 2～4 题，用问题卡。**「不知道」和「跳过」都记为该项已回答，并永久关闭**。AI 产品岗的必问维度：问题定义、本人分工、关键产品决策、badcase 与迭代、技术栈、现状和链接。
5. **成稿**：按岗位选结构（AI 产品岗用「问题 / 决策 / 迭代」）。原则是「事实不增、表达自由」：可以概括、重组、提炼用户原话，不能新增事实或数字。方案卡默认按推荐方案直接写，不强制先确认。

## 四、第十五批预研：联网能力（岗位画像 / 读链接 / 公司卡）

### 方向（用户已同意）
- 不用维基百科做 RAG。只给方向时，实时抽样 5～10 条真实 JD，提炼高频技能、职责和加分项，生成带来源的「岗位画像卡」；抽样结果按「岗位 + 日期」缓存入库，作为可复用语料。外部信息只用来定方向和追问，**不得进入简历事实**。
- 读链接：用户在输入框贴链接时自动识别，读出岗位卡片（公司、岗位、地点、要求摘要，可展开原文）。读不到（Boss、猎聘等需要登录或有反爬）时，引导用户截图或复制，走已有的 OCR。
- 公司卡：由 agent 判断何时查询公司，返回官网、行业、简介，附来源；规模和成立时间等工商字段后续做增值服务（企查查价格偏高，按需再接）。
- 后端做成「岗位情报」模块，统一三个接口：`read_job_url` / `search_company` / `sample_jobs`，数据源可插拔。等 job-hunter 也需要时，再包一层 MCP 共用，现在不单独做 search MCP。

### 数据源比较
| 方案 | 计费 | 说明 |
|---|---|---|
| **DeepSeek Search / Fetch API**（首选） | 每 1000 次成功请求 5 元；失败、无结果、超时不计费 | 复用线上已有的 DeepSeek key，服务器在国内。Search：`POST https://api.deepseek.com/v1/tools/search`（`query` ≤128 字，支持 `site:` / `lang:zh` / `after:`，`count` 1–50，`need_content`）；Fetch：`POST /v1/tools/fetch`（`url`，返回 Markdown 正文）。各 5 QPS，Fetch 另有目标域名限速 |
| 阿里百炼 WebFetch / EnhancedSearch MCP | 分别免费 1000 / 200 次 | 国内可用，作为补充或对照；key 已存本机 |
| Tavily | dev key | 海外服务，国内服务器访问需走代理，作为兜底；key 已存本机 |
| 企查查开放平台 | 按次计费、偏贵 | 只有规模、成立时间、行业、融资几项对求职者有用，放到增值服务 |

key 存在本机 `~/.config/huhua/llm-keys.env`（`TAVILY_API_KEY`、`BAILIAN_WEBSEARCH_MCP_KEY`）；上线时写入服务器 `deploy/app.env`，不进代码仓库。
