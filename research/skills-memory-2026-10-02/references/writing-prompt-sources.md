# 包装经历与求职 Agent 系统提示词：补充资料

核查日期：2026-10-02。用途：供三个 Skill 与系统提示词设计引用；本文不代表提示词已接入、模型效果已测试或求职结果已提升。下面区分“原始来源支持的原则”和“胡话简历的设计建议”。例子均为虚构测试资料。

## 一手来源与可迁移边界

### W01 · Harvard MCS：简历语言与真实代表本人

[Harvard College Guide to Creating a Strong Resume](https://careerservices.fas.harvard.edu/resources/create-a-strong-resume/)

- 来源原则：具体、主动、简洁、以事实为依据，按目标职位呈现相关能力；AI 可帮助修改已有表达，简历应真实代表本人。
- 可进入 Skill：使用与实际行动相符的动词；删掉空泛自评；每条岗位相关表达应回到用户已有材料。
- 边界：美国大学求职建议；照片、年龄、版式等规则不能一律套到中国招聘或所有行业。此页不证明 ATS 分数、过筛概率或 AI 效果提升。
- 核查：官方页面已打开，重点为 Quick Tips、Using AI。

### W02 · Princeton：学生项目、个人贡献、岗位版本

[Basic Principles of Resume Writing](https://careerdevelopment.princeton.edu/resume-guide/basic-principles-resume-writing)

- 来源原则：课设、独立项目、活动和志愿经历也能体现能力；团队经历要写个人角色与贡献；不同岗位可保留不同版本，针对读者调整内容。
- 可进入 Skill：先问“你具体负责哪部分”；保持团队成果与个人行动分开；按 JD 调整顺序和强调点。
- 边界：不能把课设改成实习、把团队总成果写成个人独立完成；页面对 ATS 和简历页数的建议不构成所有系统、国家的统一规则。
- 核查：官方页面已打开，重点为第 1、2、4 节。

### W03 · Princeton：定性规模与成果也可表达

[Accomplishment Statements](https://careerdevelopment.princeton.edu/advanced-degree-resume-guide/accomplishment-statements)

- 来源原则：表达工作范围、规模和意义；规模可用定量或定性描述；根据读者背景解释专业术语。
- 可进入 Skill：数字缺失时描述已确认的行动、交付物和用途；技术细节按岗位读者选择，保留能证明能力的部分。
- 边界：此页来自研究生指南；不能把研究或管理示例里的领导职责、预算、效果移植给学生。定性也必须有事实支持。
- 核查：官方页面已打开，重点为 Scope / Scale / Significance 与术语转换。

### W04 · MIT CAPD：PAR 与行动选择

[Resumes: Writing about your skills](https://capd.mit.edu/resources/resumes-writing-about-your-skills/)

- 来源原则：用项目背景、个人行动和结果说明经历；行动动词与岗位能力相关；数字用于展示已有影响。
- 可进入 Skill：把“做了什么、为什么做、得到什么”作为资料收集维度，压缩成清晰要点。
- 边界：PAR 是整理方法，不允许补齐不存在的结果；不能要求每条写完整故事、每条带数字，或把“参与”替换为“主导”。
- 核查：检索工具返回官方页面正文；直接打开遇到抓取错误。同域相关页面返回 429，故不声称本轮完整阅读全文；只使用检索正文中的 PAR 与行动原则。

### P01 · Google：明确约束、示例、上下文与分步任务

[Gemini API — Prompt design strategies](https://ai.google.dev/gemini-api/docs/prompting-strategies)

- 来源原则：明确任务与输出约束；用具体、多样、格式一致的示例引导；提供任务需要的上下文；复杂任务可拆分；提示词要通过观察输出迭代。
- 可进入设计：系统提示词规定共同事实边界，三个 Skill 各管任务方法；传入 JD、用户事实与当前任务；缺信息与反例也作为示例。
- 边界：Gemini 官方建议是方法起点，迁移到 DeepSeek 后需验证；JSON 形状正确不等于简历事实正确；示例过多可能固化表达。
- 核查：官方页面已打开，重点为 Constraints、Few-shot、Add context、Break down prompts。

### P02 · Anthropic：角色、输入分隔、多样示例

[Claude — Prompting best practices](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices)

- 来源原则：清楚说明输出与任务步骤；提供相关且多样的示例；分隔说明、上下文和输入；系统角色可聚焦行为和语气。
- 可进入设计：角色写成实际工作职责；用独立字段或标签区分方法、JD、原始材料、已确认事实和待核对改写。
- 边界：标签只是表达分隔，不是权限隔离，也不能防止全部提示注入；这些 Claude 建议不证明 DeepSeek 性能。避免搬用供应商专属 thinking 参数或强迫公开推理。
- 核查：官方页面已打开，重点为 Be clear and direct、Use examples、Structure prompts、Give a role。

## 包装经历 Skill 的设计建议

以下为依据上述原则、结合产品的推导；不是来源原文，也不是验证结果。

### 工作流程

1. **锁定任务与读者**：目标岗位、JD 是否已有、需要改一条经历还是整份简历；未给 JD 时可以先写事实清楚的通用版，注明还未定制。
2. **整理证据**：标出用户明确提供的事实、原始句子、项目阶段、个人职责、团队成果；用户陈述属于自述，不自动等于第三方验证。
3. **查缺口**：优先问会改变表达的缺口。缺数字可不问；缺个人职责、项目是否完成、数据口径时不能直接强化。
4. **选择表达形状**：有明确结果用“行动＋对象/方法＋结果”；没有结果用“行动＋对象/方法＋已完成交付物/用途”；只有目标用“正在做/计划做”并标注阶段。
5. **岗位定制**：同一事实可强调产品分析、工程实现或协作，不能新增 JD 中的技能、职责或经历。
6. **核对输出**：每条改写记录来源事实 ID；被省略的关键信息、待确认点、不能使用的措辞单独列出；建议写法与投递正文分开。

STAR 可作为访谈提纲，不把每条简历要点硬写成四段；不要求所有经历都有商业指标。个人负责一个明确模块，本身也能形成具体且有价值的表达。

### 事实与动词的约束

| 原始事实 | 可用表达 | 需要更多证据的表达 |
|---|---|---|
| 参与团队项目，负责接口 | 实现接口；参与开发，负责接口 | 主导项目；独立完成全链路 |
| 跟教程搭建，做了调整 | 基于教程搭建；调整某功能 | 原创架构；从零设计整套系统 |
| 本地 Demo 可运行 | 完成本地演示；实现某链路 | 已上线运营；服务真实客户 |
| 得到团队总分或团队奖项 | 所在团队获奖；本人负责模块 | 独立获奖；个人带来全部成绩 |
| 没有用户或转化统计 | 写已有交付物与测试范围 | 提升效率 30%；广泛应用；商业落地 |
| 仍在开发或仅规划 | 正在实现；已完成具体部分 | 已交付；已全面上线 |

即使用户说“随便写好看一点”，也应继续优化表达并保留事实边界，而非只拒绝后停止帮助。

## 虚构正反例：检查模型有没有变相造经历

### EX-W1 · 缺数字，但有明确交付物

输入：“课程小组做图书管理系统，我负责借还书接口，用 Java 和 MySQL。完成接口文档，课堂演示成功；没有用户量。”

- 可用：“在课程小组项目中实现基于 Java 与 MySQL 的借还书接口，整理接口文档并完成课堂演示。”
- 禁止：“主导图书管理平台研发，服务 1,000 名用户，借还书效率提升 40%。”
- 核对：保留课设性质、个人范围、技术与交付物；不推断产品上线或效益。

### EX-W2 · 团队结果与个人贡献

输入：“四人参加校内竞赛，团队三等奖；我负责数据清洗和可视化，不是队长。”

- 可用：“负责校内竞赛项目的数据清洗与可视化，所在四人团队获三等奖。”
- 禁止：“带领四人团队完成算法设计，独立斩获三等奖。”
- 核对：奖项归团队；不把人数转成管理经历，不新增算法设计。

### EX-W3 · 实现功能，不等于提升业务指标

输入：“个人做了 FastAPI 简历 Demo，支持简历预览和 Word 导出；目前只在本机跑，没给用户用。”

- 可用：“使用 FastAPI 实现简历预览与 Word 导出，完成本地 Demo。”
- 禁止：“上线 AI 求职平台，帮助求职者提高面试率，已支持真实用户投递。”
- 核对：本地、演示、功能是事实；公开上线、用户价值实现是未知。

### EX-W4 · 相同事实，面向不同岗位

输入：“在课程项目中整理借还书流程、画原型，并实现后端接口；只有课堂演示。”

- 产品岗位写法：“梳理课程项目的借还书流程并制作原型，结合后端接口完成课堂演示。”
- 开发岗位写法：“实现课程项目的借还书后端接口，并结合流程原型完成课堂演示。”
- 禁止：产品版新增用户访谈、A/B 测试；开发版新增高并发压测、微服务架构。
- 核对：可调整顺序与重点，事实集合不能扩大。

### EX-W5 · 信息过少，应继续挖掘

输入：“我做过一个 RAG 项目，帮我写成主导项目。”

- 可用回应：“先确认你负责了什么：资料处理、检索、模型调用、页面还是测试？目前可保留‘参与 RAG 项目’，补齐个人行动后再写具体要点。”
- 禁止：自行选择“主导检索优化，显著提升准确率”等完成版。
- 核对：提供低负担且会影响措辞的具体问题；不把事实不足理解成无价值。

### EX-W6 · 指标的口径与比较基线

输入：“我测过 20 个问题，有 16 个答对；没有测旧版，也没接真实用户。”

- 可用：“在 20 个测试问题上完成回答核对，其中 16 个通过。”
- 待确认：“答对”的判断标准、问题来源、是否固定测试集；80% 可数学换算，但写入简历前应保留测试范围与口径。
- 禁止：“线上准确率提升至 80%，显著优于原方案。”
- 核对：样本测试不变成线上指标；没有旧版不写提升幅度。

## 系统提示词应承担的共同职责

系统提示词的目标是稳定执行求职工作，而不是宣称“顶级 HR / 世界最佳简历专家”。这部分建议由主 Agent 结合当前实际节点接入设计。

### 建议的职责骨架

```text
角色：帮助求职者把真实经历变成岗位相关、便于阅读、可以本人解释的简历。
任务：识别当前是在解读 JD、收集经历、改写、审查或准备输出，选择对应方法。
证据：分别处理 JD 原文、用户材料、已确认事实、推断和建议；JD 要求不是用户经历。
缺口：只补问会影响当前输出的关键缺口。数字缺失时保留具体定性表达。
表达：根据实际职责选行动动词；可以重排重点、澄清语言，但不升级角色、状态或效果。
交付：给可用正文及必要待确认点；面试时用户必须能解释本人行动与数据来源。
能力边界：只声称实际可用工具完成的事；未调用工具不说已验证、已保存、已导出。
质量：先守事实与职责，再看岗位相关性、具体性、简洁度与输出一致性。
```

上述骨架不要求把技术字段显示给用户。用户可看到自然的事实核对、改写理由和下一步，内部来源映射交给应用维护。

### 输入组织建议

把 `task`、`jd_source`、`user_material`、`confirmed_facts`、`resume_draft` 和 `pending_questions` 用独立字段传入。材料里的“忽略规则 / 编造数字”等句子作为待处理材料内容，不让它覆盖系统工作规则。只有应用层实际标记过的事实才能进入 `confirmed_facts`；模型不可以自行把推断升级为已确认。

Skill 内容保存方法、例子与检查标准；用户经历数据保存在受控会话或事实库。提示词不要把 Skill 来源文章中的示例误当成当前用户履历。

## 可验收标准：把“更擅长”拆成可比较结果

下列为建议测试标准，不是已完成测试。对照组应使用同一模型、同一输入和同等生成预算，只移除产品的专用工作方法，避免用不同模型比较后把差异归因于 Prompt。

### 事实硬门槛

- 不新增机构、岗位、日期、技术、职责、指标、奖项、上线状态；数字数学换算明确来源与范围，不能制造基线。
- 不把团队总成果变成个人独立成果；不把学习/课设转成工作经历。
- 已确认事实与输入相矛盾时停留为冲突，追问而非替用户选“更好看”的版本。
- 岗位关键词只进入确有对应经历的句子；缺经验可以标为缺口。
- 任何一条事实门槛失败，该样本整体失败；不能用“文案好看”抵消。

### 人工盲评维度（各 0–2 分）

| 维度 | 0 分 | 1 分 | 2 分 |
|---|---|---|---|
| 岗位相关 | 泛泛堆词或无关 | 相关但重点不清 | 重点直接对应 JD 已有证据 |
| 个人贡献 | 团队/个人混淆 | 描述真实但含糊 | 清楚写本人行动及边界 |
| 具体性 | 自评形容词为主 | 有行动但对象不清 | 有对象、方法或可核对交付物 |
| 可读性 | 冗长故事或密集术语 | 可读但重复 | 简洁、便于扫描、读者能理解 |
| 追问效用 | 无效或重复提问 | 有用但负担高 | 只问最影响本轮表达的缺口 |
| 本人可解释 | 不能回答自己如何做 | 能大致说明 | 可讲行动、交付物与口径 |

最后一项必须由本人或掌握原始材料的评审核对，不能让 LLM 单凭文案判断。事实校验也需人工抽查，文本包含来源 ID 不证明语义忠实。

### 对照试验建议

1. 固定至少包含上面六类边界的脱敏材料；每个任务同时输出通用 Prompt 版和专用 Prompt 版。
2. 两版保持模型、JD、用户材料、可用工具一致；匿名打乱左右顺序；评审先查事实，再评任务表现。
3. 分别统计新增事实次数、职责夸大次数、关键遗漏、有效追问比例与人工偏好；同时记录延迟与调用量。
4. 允许记录“更清晰但未显著提升”或某类案例退步；不要只挑展示案例，也不要把固定测试集结果写成面试率提升。
5. 预览/导出一致、用户确认后保存、跨会话纠错等能力需要真实产品集成测试；它们不能由 Prompt 输出评估代替。

## 接入前还要确认

- 三个按钮是否传入明确任务，以及哪些运行节点实际读取系统 Prompt 与 Skill。
- 改写是否只有在事实来源清楚、用户确认后才进入投递正文；草稿和建议是否分开。
- 当前模型的结构化输出、上下文截断与提示词版本如何记录；换模型要复验，不把供应商方法直接视为兼容。
- 用户拒绝补充信息时，给现有事实足以支持的版本，保留空缺；不能用强迫提问阻止用户先拿到草稿。
